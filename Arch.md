# Архитектура маркетплейса

## C4 Container Diagram

---

## 1. Домены и их ответственность

| Домен | Зона ответственности |
|-------|---------------------|
| **Пользователи (User)** | Регистрация, аутентификация, авторизация, управление профилями покупателей и продавцов, роли и права доступа |
| **Каталог товаров (Product/Catalog)** | Создание, редактирование и удаление товаров продавцами. Категории, поиск, фильтрация, управление остатками |
| **Заказы (Order)** | Оформление заказа, хранение состава заказа, управление жизненным циклом заказа (создан → оплачен → доставлен → завершён) |
| **Платежи (Payment)** | Приём оплаты, расчёт итоговой суммы, обработка возвратов, хранение истории транзакций |
| **Доставка (Delivery)** | Создание отправлений, отслеживание статусов доставки, интеграция с логистическими провайдерами |
| **Рекомендации (Recommendation)** | Персонализированная лента товаров на основе истории просмотров, покупок и предпочтений пользователя |
| **Уведомления (Notification)** | Отправка уведомлений пользователям (email, SMS, push) о статусах заказов, оплаты и доставки |

---

## 2. Распределение доменов по сервисам

| Сервис | Домен(ы) | Логика разбиения |
|--------|----------|-----------------|
| **User Service** | Пользователи | Аутентификация — критичный компонент. Изолирован для независимого масштабирования и повышенной безопасности. Частота изменений отличается от бизнес-логики |
| **Product Service** | Каталог товаров | Каталог — ядро маркетплейса с высокой нагрузкой на чтение. Выделен отдельно для независимого масштабирования и кэширования |
| **Order Service** | Заказы | Заказ — центральный бизнес-процесс, связывающий покупателя, товар и оплату. Отдельный сервис, чтобы изолировать сложную бизнес-логику состояний |
| **Payment Service** | Платежи | Финансовые операции требуют повышенной надёжности, аудита и соответствия стандартам (PCI DSS). Изоляция обязательна |
| **Delivery Service** | Доставка | Логистика имеет свой жизненный цикл, не зависящий от заказа. Интеграция с внешними провайдерами удобнее в отдельном сервисе |
| **Recommendation Service** | Рекомендации | Алгоритмы рекомендаций ресурсоёмки и могут использовать другой стек (Python/ML). Изоляция позволяет масштабировать независимо от остальной системы |
| **Notification Service** | Уведомления | Отправка уведомлений — вспомогательная функция. Выделена отдельно, чтобы сбой в отправке email не влиял на оформление заказов |

Принцип разбиения: **один домен = один сервис**. Каждый сервис имеет чёткую бизнес-ответственность, собственный цикл разработки и может деплоиться независимо.

## 3. Границы владения данными

### Данные каждого сервиса

| Сервис | База данных | Владеет данными | За что отвечает |
|--------|------------|-----------------|-----------------|
| **User Service** | User DB (PostgreSQL) | Пользователи, роли, токены, профили | Единственный источник правды о пользователях. Никто другой не пишет в эту БД |
| **Product Service** | Product DB (PostgreSQL) | Товары, категории, изображения, остатки | Единственный источник правды о каталоге. Остатки списываются только через этот сервис |
| **Order Service** | Order DB (PostgreSQL) | Заказы, позиции заказа, статусы заказов | Единственный источник правды о заказах. Хранит ссылки (ID) на товары и пользователей, но не дублирует их данные |
| **Payment Service** | Payment DB (PostgreSQL) | Транзакции, счета, возвраты | Единственный источник правды о платежах. Хранит только ID заказа, не данные заказа |
| **Delivery Service** | Delivery DB (PostgreSQL) | Отправления, статусы доставки, трек-номера | Единственный источник правды о доставке. Хранит только ID заказа |
| **Recommendation Service** | Recommendation DB (Redis) | Поведение пользователей, кэш рекомендаций | Хранит аналитические данные. Потеря данных не критична — восстанавливается из событий |
| **Notification Service** | Notification DB (PostgreSQL) | Шаблоны уведомлений, история отправок | Единственный источник правды об уведомлениях. Хранит только ID пользователя и ID заказа |

**Разделяемые базы данных отсутствуют.** Каждый сервис владеет своей БД. Другие сервисы получают данные только через API или события.

### Взаимодействия между сервисами

#### Синхронные (REST)

| Кто | Кого вызывает | Зачем | Способ |
|-----|--------------|-------|--------|
| API Gateway | User Service | Маршрутизация запросов пользователей | REST |
| API Gateway | Product Service | Маршрутизация запросов каталога | REST |
| API Gateway | Order Service | Маршрутизация запросов заказов | REST |
| API Gateway | Recommendation Service | Маршрутизация запросов рекомендаций | REST |
| Order Service | Payment Service | Инициировать оплату при оформлении заказа | REST (синхронно) |
| Order Service | Product Service | Проверить наличие товара и списать остаток | REST (синхронно) |
| Recommendation Service | Product Service | Получить данные товаров для формирования ленты | REST (синхронно) |
| Recommendation Service | User Service | Получить предпочтения пользователя | REST (синхронно) |

#### Асинхронные (Kafka)

| Кто публикует | Событие | Кто потребляет | Что делает потребитель |
|--------------|---------|---------------|----------------------|
| Order Service | `OrderCreated` | Notification Service | Отправляет уведомление «Заказ создан» |
| Order Service | `OrderCreated` | Recommendation Service | Обновляет модель предпочтений пользователя |
| Payment Service | `PaymentCompleted` | Order Service | Обновляет статус заказа на «Оплачен» |
| Payment Service | `PaymentCompleted` | Delivery Service | Создаёт отправление |
| Payment Service | `PaymentCompleted` | Notification Service | Отправляет уведомление «Оплата прошла» |
| Payment Service | `PaymentFailed` | Notification Service | Отправляет уведомление «Ошибка оплаты» |
| Delivery Service | `DeliveryUpdated` | Notification Service | Отправляет уведомление об изменении статуса доставки |
| Product Service | `ProductViewed` | Recommendation Service | Записывает просмотр для персонализации |
